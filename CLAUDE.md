# TaskMate — mémoire projet

**Langue : réponds toujours en français** (messages, résumés, rapports, descriptions de PR). Le code et les identifiants suivent les conventions du repo ; les messages de commit restent en français.

**Autonomie : ne demande jamais de confirmation à l'humain** pour les actions courantes de développement. Décide, applique, trace dans `DECISIONS.md`. Tu t'arrêtes uniquement pour une action irréversible ou qui exige un compte/secret que tu n'as pas (voir `HUMAN_TODO.md`).

App mobile familiale (Expo + Supabase). Spéc: `SPEC.md` (fait autorité). Travail: `PROGRESS.md`, `DECISIONS.md`, `HUMAN_TODO.md`.

## Commandes
- Install: `pnpm install` (racine)
- Dev: `pnpm --filter @taskmate/mobile start`
- Vérifs: `pnpm -w typecheck`, `pnpm -w lint`, `pnpm -w test`, `pnpm --filter @taskmate/mobile exec expo export --platform ios`
- DB (Docker dispo): `supabase start`, `supabase db reset && supabase test db`, `supabase db lint`
- DB (sans Docker, cf. D-002): `./scripts/db-test.sh` (Postgres 16 local + pgTAP + shim Supabase + `db-concurrency.sh`)
- Types DB : `supabase gen types typescript --local > apps/mobile/src/types/db.ts` (aujourd'hui écrits à la main, D-009)
- Web (cible principale, D-025) : `pnpm --filter @taskmate/mobile export:web` → `apps/mobile/dist` ; implémentations web = fichiers `*.web.ts(x)` à côté des natifs (D-026)
- Production : Supabase (Sydney) via l'intégration GitHub (migrations auto à la fusion sur main, D-043) ; santé du serveur : Réglages → Diagnostic (`diagnostics()` + sondes, D-045)
- E2E web : `apps/mobile/e2e-web/README.md` (Playwright, Supabase local) ; déploiement : `vercel.json` (racine) ; HUMAN_TODO.md liste ce qui demande vos comptes (Supabase cloud, Vercel)

## Architecture
- `apps/mobile/app` : écrans Expo Router uniquement. Écrans → hooks (`src/hooks`) → `src/api` (client Supabase, RPC typés) ; calculs purs dans `src/domain` (couverture ≥ 90 %).
- `src/sync` : persistance TanStack Query, file de mutations hors ligne ; `src/store` : session/rôle ; `src/i18n` : vi (défaut), fr, en.
- `supabase/migrations` : schéma + RLS + RPC + cron ; `supabase/tests` : pgTAP ; `supabase/functions` : Edge Functions.
- Alias `@/` = `apps/mobile/src/`.

## Règles non négociables
- Jamais de secret dans git (seulement `.env.example`). Jamais `--no-verify`, test skip, `@ts-ignore`, RLS relâchée.
- Jamais d'écriture client directe dans `point_transactions` ni `tasks.completed_at` : RPC §5.2 uniquement.
- Toute nouvelle table : RLS dans la même migration + tests pgTAP positifs ET négatifs.
- Aucune chaîne UI en dur (i18n). `accessibilityLabel` + cibles ≥ 44 pt. Aucun écran ne compare/classe les deux enfants.
- `date` d'une tâche = jour local de la famille, jamais dérivé d'un timestamp UTC.
- Ne pas modifier SPEC.md. Pas de `push --force`, pas de réécriture d'historique.
- Git : tu **commites et pousses** sur la branche de travail sans demander, puis vérifies la CI (`gh api repos/{owner}/{repo}/actions/runs`) ; ne déclare jamais la CI verte sans l'avoir constatée. Si une PR est possible (branche de destination distincte), ouvre-la toi-même ; sinon, dis-le en une ligne.
- Fusion et déploiement (décision de Teo, 2026-10-14) : quand la CI de la PR (`app`, `db`, `e2e`) est VERTE sur la tête courante, fusionne en merge commit (sans supprimer la branche) SANS demander, puis constate la CI de `main`, le déploiement Vercel (`READY`) et, s'il y a une migration, son application (`list_migrations`) ; rouge ou non constatée = ne pas fusionner. Cela couvre le déploiement automatique par fusion (Vercel, intégration Supabase), rien d'autre.
- Interdit sans l'humain : publication store, création de projet/ressource cloud, écriture de secrets de production, action destructive sur la production (suppression de données, rollback), déploiement hors de la fusion d'une PR verte.

## État
Jalons M0 → M11 + corrections C1 → C4 livrés (voir PROGRESS.md → rapport final). Spec v4 : l'enfant ne crée/modifie rien ; il coche → `pending`, le parent valide (`validate_task`) → points. Types DB générés (`src/types/db.ts`, contrôlés en CI) ; ne pas les éditer à la main. Captures de comparaison : `tools/visual`. Comptes (D-050) : parent = Google (inscription Google uniquement, e-mail+mot de passe réservé aux comptes existants), plusieurs parents par famille (invitation à code haché 24 h, `parent_invites`) ; enfant = identifiant (unique par famille) + mot de passe créés par un parent via les Edge Functions `create-child` / `reset-child-password` / `delete-child`, connexion par `child-login` SEULE (e-mail d'un parent + identifiant + mot de passe vérifié contre un haché bcrypt, verrouillage IP/famille ; GoTrue n'a qu'une adresse UUID et un mot de passe aléatoire : aucune connexion directe, D-051) ; service_role fournie par l'environnement des fonctions, jamais dans le code ; plus d'OTP, de QR ni de connexion anonyme.
Règle D-052 (déroge à la spéc v4, décision de Teo) : un enfant ne voit QUE ses propres données (ni frère/sœur, même en lecture seule) — imposé par la RLS (migration `…000014`), pas seulement par l'UI ; le cache persisté est purgé au changement d'utilisateur.
Génération IA des questions (D-057, D-060, PR B) : Edge Function `generate-questions` (fournisseur OpenAI derrière l'interface `AiClient`, parent, document non conservé ni journalisé, sortie JSON stricte revalidée côté serveur, brouillon seulement, quota quotidien) ; secret `OPENAI_API_KEY` à ajouter par l'humain (HUMAN_TODO § 6 bis) ; jamais d'appel IA réel en CI/tests.
Supports multiples (D-061) : type de support enregistré sur le jeu (examen, examen avec corrigé, cours, liste ; « Auto » par défaut, détecté par l'IA et corrigeable), nombre « Auto » plafonné côté serveur (30), signalements `to_verify`/`needs_figure` et confirmation des réponses dans la table de la clé (jamais visibles de l'enfant) ; la base REFUSE la publication tant qu'une réponse « à vérifier » (tous types) ou, pour un examen, non confirmée, n'est pas confirmée par le parent.
Support papier (D-062) : `quiz_sets.paper_support` / `answer_sheet_only` (réglés par la RPC `set_quiz_paper_support`, défaut selon le type) ; un jeu papier n'est jamais mélangé (questions par numéro d'origine, lettres A–D de la feuille) ; l'enfant voit le numéro d'origine et « dépend d'une figure » par les RPC (jamais `to_verify`/`confirmed`) ; en « feuille seule » le SERVEUR n'envoie que des lettres.
Révisions (D-055, D-059) : QCM relus par le parent, un seul parcours (pas d'entraînement), jamais de bonne réponse côté enfant avant validation ; après validation, correction visible seulement si le parent l'a activée en validant, ordre des questions et choix mélangé par le serveur à chaque tentative ; la clé des réponses n'est lisible que par le parent (table dédiée + RPC `security definer`), points non reliés.
Apparence (D-064, D-069, D-070, D-072, D-073) : cinq thèmes au choix par appareil — « verre givré bleu-gris » (défaut, `docs/mockups/style-reference.webp`, déroge à SPEC §6.2), « kawaii » (`docs/mockups/theme-kawaii-reference.png`), « cosmos », sombre (`docs/mockups/theme-cosmos-reference.png`) et « teddy », nounours chocolat sur rose poudré (`docs/mockups/theme-teddy-reference.png`) et « bunny », lapinous pastel sur vichy bleu ciel (`docs/mockups/theme-bunny-reference.png`) ; un thème = un jeu complet de jetons dans `src/theme/themes/` (mêmes clés, contrastes testés). Utiliser UNIQUEMENT les jetons de `src/theme/tokens.ts` (`colors`, `line`, `shadow*`, `chartTones`, `hasDecor`, `decor`) et les composants `GlassTile`/`RoundButton`/`NavyPanel`/`Card`, jamais de couleur ni d'épaisseur de filet en dur ; jamais de fond translucide sur un thème illustré (D-076 : `colors.*Tint` opaques ou `tint()` de `theme/tint.ts`) (texte sur fond de couleur : `onPrimary` / `onSolid` / `onTile` / `onNavActive`, jamais `text` : il est clair en cosmos) ; couleurs d'enfant affichées via `childColor()` ; décors seulement si `hasDecor`, toujours via `components/decor/Decor.tsx` (`Mascot`, `TopOrnament`, `SectionMark` ; `kawaii` = chiens, `cosmos` = astronautes, `teddy` = oursons, `bunny` = lapinous), jamais d'illustration choisie dans un écran.
Avatar IA (D-071) : l'enfant (ou un parent pour lui) charge un portrait, l'Edge Function `generate-avatar` (OpenAI `images/edits`, secret `OPENAI_API_KEY`) le transforme en dessin enregistré comme CANDIDAT puis validé ; consentement du parent enfant par enfant (`child_avatars.ai_allowed`, RPC `set_avatar_ai_allowed`) ; la photo n'est JAMAIS conservée ni journalisée (seul le dessin WebP l'est) ; quota par enfant et par jour ; un enfant ne voit que son avatar (D-052) ; afficher un avatar par `<Avatar />` (jamais d'initiale en dur) ; web/PWA seulement.
Quiz de la semaine (D-079) : l'enfant a toute la semaine ; ses réponses sont enregistrées au fil de l'eau (`save_quiz_progress`, file de mutations `writes`, table `quiz_attempt_progress` sans AUCUN droit direct : RPC seulement, jamais de correction dedans) et restaurées sur tout appareil (`child_quiz_progress`) ; `submit_quiz_evaluation` reste la seule source du résultat ; date limite `quiz_sets.due_on` en JOUR LOCAL de la famille (`set_quiz_due_on`, dimanche suivant proposé), information seulement : le retard ne bloque JAMAIS l'enfant ; le parent ne lit qu'un nombre de réponses (`quiz_progress_counts`).
Catalogue de QCM et espace administrateur (D-080) : `platform_admins` (RLS fermée, aucune ligne dans git : requête SQL de HUMAN_TODO § 6 quater), vérification admin TOUJOURS côté base (`catalog_require_admin`, `is_platform_admin`, `ai_target_admin`) ; tables `catalog_quizzes` / `catalog_questions` / `catalog_answer_keys` / `child_subjects` sans AUCUN droit client (RPC seulement) ; l'enfant reçoit les QCM publiés de SON pays + SA classe + ses matières activées, ouverts au jour LOCAL de la famille (dates du catalogue + 7 × décalage ±4 semaines), l'échéance ne bloque jamais ; classe, matières et décalage = parent seul (RPC) ; le parent ne lit les bonnes réponses d'un QCM que par `parent_attempt_review`, une fois la tentative de SON enfant envoyée ; `quiz_attempts.catalog_id` XOR `set_id`, questions lues par `quiz_attempt_items` ; `generate-questions` mode `catalog` réservé à l'admin (403 avant tout quota). L'import par famille reste en place.
Import d'administration (D-081) : UN fichier Word/PDF à blocs `[QUIZ]` (Pays, Classe, Matière, Semaine, Titre, Ouverture, Échéance, questions, `Đáp án`, `Giải thích … Nguồn …`), lu sans IA par `domain/catalog-import.ts` après extraction du texte sur l'appareil (`domain/docx-text.ts`, pdf.js chargé à la demande), validé en entier avant toute écriture (tout ou rien, bloc + ligne) ; classes en LISTE FERMÉE par pays (VN 1–12 ; FR CP, CE1, CE2, CM1, CM2, 6E, 5E, 4E, 3E, 2DE, 1RE, TERM) normalisées par `normalizeGradeFor` / `catalog_normalize_grade` (mêmes cas testés, VN ≠ FR) ; `create_catalog_draft` écrit brouillon + dates dans UNE transaction, rejouable (ids fixés) ; case occupée = Ignorer (défaut) ou Remplacer (brouillon sans tentative), jamais d'écrasement silencieux ; `services/documentText.ts` et `.web.ts` ne s'importent JAMAIS l'un l'autre (même nom de module selon la plateforme). Fichier sans `[QUIZ]` = repli IA (D-080).

Notifications (D-088) : `activity_log` reçoit `quiz_submitted` (première soumission seulement) et `quiz_validated` (validation effective seulement) par `submit_quiz_evaluation` / `validate_quiz_attempt` ; `send-push` les envoie aux parents / à l'enfant concerné (jamais à un frère/une sœur), regroupe sur 10 min, préférences `quizSubmitted` / `quizValidated` (absentes = activées) ; l'état « activé » d'un appareil vient de la base (`my_push_status`, `domain/web-push.ts` : `deviceState`, `shouldHeal`), jamais du seul abonnement du navigateur ; `send-push` modes `status` / `test` authentifiés par la session (jamais de valeur de secret, seulement des booléens et compteurs) ; réponse `skipped:{noRecipient,noDevice,prefOff,noVapid}`.

Assistant de première connexion (D-090) : `onboarding_progress` (une ligne par PARENT : langue confirmée, étapes passées, carte masquée ; RLS « sa ligne seulement », aucune écriture client, RPC `onboarding_state` / `onboarding_set` / `onboarding_hide_card` / `onboarding_restart`) ; « fait » CALCULÉ d'après les vraies données par `domain/onboarding.ts` (une étape passée reste « à faire ») ; lancement automatique UNIQUEMENT pour une famille sans enfant (`resolveEntryRoute` → `/onboarding/setup`), jamais pour une famille existante (carte seulement) ; parent invité = assistant court (langue + notifications) ; routes `/onboarding/setup/[step]`, `/onboarding/child-setup` (enfant, une fois par appareil) ; le mot de passe d'un enfant n'existe que dans l'état local de l'étape 2 ; modèles de tâches/récompenses dans `domain/onboarding-templates.ts` ; la carte ne compare ni ne classe les enfants.
